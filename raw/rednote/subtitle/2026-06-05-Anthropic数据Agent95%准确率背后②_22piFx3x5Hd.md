## 开篇：四层架构总览

[00:00] 上次我们说在 Anthropic 内部，95% 的业务分析查询已经由 Claude 自动处理，整体准确率大约 95%。

[00:06] 这个结果并不是因为 Claude 突然更会写 SQL。

[00:08] Anthropic 把数据分析当成上下文和验证问题来处理。

[00:11] 系统首先要对付三类失败：概念歧义、数据过期、检索失败。

[00:14] 那具体怎么对付？

[00:16] 这一期我们看他们的四层系统。

[00:17] 这四层联起来，是一条从混乱数据到可信答案的工程链。

[00:21] 你可以先把它想成一套导航系统：先把地图画清楚，再规定路线，再给驾驶规则，最后检查有没有开错。

[00:30] 先整理到机器能读懂，少量官方数据集，强制使用路径，可维护的元数据和数据模型一起更新的文档。

[00:35] 放到导航里，就是先把地图画清楚——哪些路是主路，哪些路已经废弃，不能让司机在一堆长得差不多的小路里猜。

[00:41] 第二层叫可信来源。

[00:43] 它做的是告诉 Agent，查答案时先信哪里。

[00:45] 优先用语义层，再看血缘图、参考文档和业务上下文。

[00:49] 放到导航里，就是给出推荐路线——先走官方高速路，走不通再看备用路线，别自己抄小路。

[00:54] 第三层是 Skills。

[00:55] 它做的是把资深分析师的工作顺序写下来：先澄清什么，先查哪里，什么时候不能直接写 SQL，最后怎么复核。

[01:01] 放到导航里，就是给司机一份驾驶规则——知道目的地，也知道路上遇到岔路、施工和限速时怎么处理。

[01:06] 第四层叫验证。

[01:08] 它做的是上线前后持续检查：离线评测先考试，线上用来源追溯、监控和用户纠错把路上的问题抓回来。

[01:14] 放到导航里，就是导航结束后还要复盘——有没有走错路，哪段路标不清楚，下次要把地图改掉。

[01:20] 所以模型没有直接被丢进数仓里自由发挥，它是在一套被设计过的路径里工作：地图清楚、路线可信、驾驶规则明确，结果还能被检查。

[01:28] 接下来我们就放慢速度，一层一层拆。

## 第一层：数据基础

[01:30] 第一层叫数据基础。

[01:31] 它要解决的是在 Agent 开始搜索之前，先把数据世界整理到足够清楚。

[01:35] 传统数据工程当然要做模型稳定、转换可靠，数据有新鲜度和完整性检查。

[01:39] AI 时代的变化在于，数据模型的直接使用者变了。

[01:42] 以前直接面对数据模型的通常是数据科学家、数据分析师、数据工程师。

[01:47] 他们知道哪张表靠谱，哪张表废弃了，哪个字段不能直接用，某个指标要排除哪些异常情况。

[01:52] 现在业务用户问 Claude，Claude 代表用户去查数据。

[01:55] 换到现在，直接面对数据模型的变成了 Agent，但这个 Agent 背后服务的人，可能完全不懂数据基础设施。

[02:01] 比如一个销售负责人问：上个月企业客户收入增长多少？

[02:05] Claude 给了一个数字 23%。

[02:07] 这个销售负责人通常不会去检查：Claude 查的是不是官方收入表，有没有排除退款和测试账号，有没有按正确时区，数据是不是更新完了，有没有用到已经废弃的字段。

[02:15] 所以验证责任不能丢给最终用户，最终用户没法判断底层是否正确。

[02:20] 这就是为什么第一层必须提前做好。

[02:22] 在这个前提下，Anthropic 特别强调四个做法。

### 做法一：创建官方数据集（Canonical Data Sets）

[02:24] 第一，创建官方数据集。

[02:26] Canonical Data Sets。

[02:27] 它的重点不在于把所有数据都整理得很漂亮，而是先挑最核心、最常问、最容易错的概念。

[02:32] 到底哪张表、哪套字段、哪套指标定义为准？

[02:35] 比如用户收入、订单、活跃、留存。

[02:38] 先别追求覆盖全公司所有角落，先把这些高频概念收成标准答案。

[02:41] 拿收入来说，公司里可以有原始支付、每日收入、签约收入、确认收入、扣退款后的收入、财务最终口径这些层次。

[02:46] 这些表可以为了性能缓存、汇总继续存在，但它们应该从官方模型派生出来，而不是各自另起一套定义。

[02:54] 否则用户问一句"收入是多少"，Agent 面前就是 40 个看起来都能用的版本。

[02:58] 这一层要做的是提前把候选选项减少，非官方的进行版本要么废弃、要么降级、要么标注编辑。

[03:04] 最后让 Claude 收一个概念时，稳定碰到一个被治理过的答案。

### 做法二：标准要强势执行

[03:07] 第二，标准要强势执行。

[03:08] 口头上说"用官方口径"没用，团队为了方便还是会建临时表、试图用临时口径。

[03:13] 所以 Anthropic 会从三个地方强制执行：

[03:15] **工具层面**：把 Agent 结构性地导向官方模型、语义层，不让它一上来乱翻原始表。

[03:20] **代码检查层面**：如果有人绕过官方模型或者改了模型，却没有更新相关说明，CI 会拦住。

[03:25] **组织层面**：下游团队要基于治理层构建，不这么做就要解释原因。

[03:29] 治理的重点是：标准不能只写在文档里。没有执行力的数据治理，几个月后又会变回一堆相似表。

### 做法三：供给维护（Co-location）

[03:34] 第三，供给维护。

[03:36] 也就是把数据建模代码、语义层定义、参考文档、官方看板定义、数据测试、Claude 要读的 Schema 文档，全部放进同一个代码仓库，让它们进入同一个变更流程。

[03:45] 文件摆在一起只是表面，重点是让系统看见它们之间的依赖关系。

[03:49] 举一个具体例子：有人改了收入模型，把字段从总收入改成净收入，或者把收入口径从不扣退款改成扣退款。

[03:55] 如果收入文档、看板定义、Schema 还写着旧口径，Claude 后面就会按旧说明查新数据，答案自然会错。

[04:00] 这些东西如果分散在不同地方——比如模型在代码仓库，指标说明在文档工具，看板在 BI 工具，Schema 在另一个平台——系统很难知道它们互相影响。

[04:09] 但如果它们在同一个变更流程里，提交改动时 CI 就可以做依赖检查：

[04:12] 你改了收入模型，但有没有同步改收入文档？有没有碰收入相关的 Schema？看板还引用着过时的字段吗？文档里有没有继续引用已经删掉的字段？

[04:19] 它不一定知道你应该怎么改，但它能发现一个危险信号：你动了 Claude 会依赖的数据模型，却没有更新 Claude 的说明书。

[04:25] 所以供给维护解决的是数据变了、说明书没跟着变的问题。

### 做法四：把元数据当成正式产品维护

[04:28] 第四，把元数据当成正式产品维护。

[04:31] 元数据就是：表名是什么意思，字段是什么意思，指标代表什么，谁负责，数据从哪里来，多久更新一次，这张表是官方表、实验表还是废弃表。

[04:39] 这些东西不能只当注释。对 Agent 来说，它们就是路标。

[04:42] 没有这些路标，Claude 看到用户事件表、每日活跃用户表、用户活跃最终版，还是只能靠名字猜。

[04:48] 所以第一层回答的是：先把数据世界变清楚。

[04:50] Claude 面对的是公司提前收窄过的答案空间。

---

## 第二层：可信来源（Source of Truth）

[04:53] 接下来进入第二层：可信来源，Source of Truth。

[04:56] 如果第一层是把地图本身画清楚，第二层就是导航里的路线优先级。

[04:59] 同一个目的地，先走哪条官方路，哪些路只能参考，哪些看起来像路但不能走，都要提前排好。

[05:05] 放回数据分析里，它解决的是：用户问一句人话以后，Claude 应该先信哪里，怎么把这句话对应到数据实体。

[05:10] 它告诉 Agent：有些入口是权威的，有些只能当参考，有些材料看起来像，但不能直接当真相。

### 语义层（Semantic Layer）

[05:16] 信任最高的入口是语义层。

[05:17] 语义层可以先理解成公司批准过的指标接口。

[05:20] 业务人说收入、活跃用户、留存率，语义层负责把这些词翻译成公司认可的数据定义：应该用哪张治理表，分子是什么，分母是什么，时间窗口是什么，必须排除哪些数据，可以按哪些维度切。

[05:30] 它更像一套机器可调用的官方指标目录。

[05:32] 如果问题能映射进去，Agent 就直接调用这套定义拿数。

[05:41] 不要求全公司只有一个定义。真实企业里常常会出现 10 个部门十种口径。

[05:45] 比如高价值客户：销售团队可能按金额成交额算，增长团队可能按使用频率算，客户团队可能按服务优先级算，财务团队可能只看合同金额。

[05:53] 他们都有业务理由。麻烦出在多个定义都叫同一个名字，没有适用场景，没有负责人，还能被 Agent 随便拿去算。

[05:59] 所以更合理的做法是：公司级口径保留一个默认官方定义，部门口径允许存在，但要改名、标注编辑。

[06:05] 比如公司高价值客户、销售高价值客户、增长高价值用户、客户重点客户。

[06:09] 每个定义都写清楚适用部门、适用场景、计算口径、排除条件、负责人、最后更新时间、能不能用于公司级汇报。

[06:14] 这样 Agent 遇到一句模糊提问，就不应该自己猜。

[06:17] 它要么根据上下文选择对应口径，并在答案里说明；要么停下来问：你要看公司统一口径，还是销售口径、增长口径？

[06:24] 语义层的价值是把差异显性化、可追责。

[06:27] Anthropic 的 Agent 在 Skill 设置里，被要求优先使用语义层。

### 反直觉实验：让 LLM 自动生成指标定义

[06:31] 但这里有一个反直觉实验。

[06:32] 他们试过让大模型自动从原始表和查询日志生成指标定义。

[06:35] 结果模型生成的定义看起来合理，却继承了原本的歧义，在评测上是负收益。

[06:39] 所以结论很克制：

[06:41] Claude 可以帮忙生成文档，指标定义要有人负责。

[06:44] Claude 可以帮你写说明，不能替公司立法。

[06:46] 指标定义不能当文案任务，也不能只看写得是否合理。

[06:49] 一旦收入、留存、活跃用户这些定义让模型自己从旧查询例总结，它很容易把旧系统里的歧义也一起继承下来。

[06:55] 比如历史查询例：有的收入扣退款，有的不扣退款；有的活跃用户按登录算，有的按核心动作算。

[07:01] 模型总结出来的定义可能写得很顺，但它没有资格替公司决定到底哪一个才算官方口径。

[07:06] 所以可以让 Claude 起草说明，但最后必须有数据 Owner 确认。

### 血缘图和业务上下文

[07:09] 当语义层覆盖不了问题时，第二个导航入口是血缘和转换图。

[07:12] 血缘回答的是：这个数字从哪里来。

[07:15] 转换图回答的是：它中间经过哪些模型，哪些聚合，哪些口径变化。

[07:18] 它告诉 Agent：这个数字从哪张原始表一路聚合上来，哪些中间模型已经过时，哪些表共享同一个粒度。

[07:24] 血缘这件事可以理解成数据的家谱。

[07:27] 比如一个收入数字，最开始可能来自原始支付事件，经过订单清洗、扣掉退款、再按天聚合，最后进到收入看板。

[07:33] 如果 Claude 只看到最后一个数字，它不知道这个数字能信到什么程度。

[07:37] 但如果系统知道血缘就能回答：这个答案来自哪张原始表，数据更新到哪天，谁负责，出了问题应该找哪个团队。

[07:45] 这是第二层里常被低估的一块。

[07:47] Anthropic 会把路线图、表名、这些业务上下文写进评测问题的生成里。

[07:51] 这说明 Agent 就需要知道公司当下的业务语境，才能提出更好的澄清问题，也更容易定位该用哪张表、哪条定义。

[07:56] 为什么业务上下文重要？因为用户的问题往往不完整。

[08:00] 比如用户问"Q2 发布以后转化率怎么样"。

[08:02] 如果 Claude 只看数据库，它不知道 Q2 发布是哪个产品，发布日期是哪天，是哪个市场，相关实验叫什么，哪个团队负责，这个问题是不是为了周四董事会准备。

[08:11] 不懂业务的 Claude 会回答用户字面问了什么，但不一定回答用户实际想问什么。

[08:15] 所以可信来源里不只有数据系统，也要有内部文档、产品路线图、角色记录、组织结构和团队职责。

[08:21] 这样 Claude 遇到"Q2 发布"、"核心客户"、"新版定价"、"董事会版本"这种隐晦说法时，才有机会判断用户到底指什么。

[08:26] 如果还不确定，它也能问出更好的澄清问题。

### 历史查询的价值与局限

[08:29] 很多人直觉上会认为，历史 SQL 应该是最高价值的参考——过去回答过的问题都有记录，直接喂给 Agent 不就行了？

[08:35] Anthropic 做过这个实验。

[08:36] 他们给 Agent 直接喂了整个看板、转换模型、分析师写的几千条 SQL 语料，并且确认 Agent 真的读过了。

[08:43] 结果准确率变化不到一个百分点。

[08:44] 他们进一步检查那些答错的问题，正确答案是否就在语料里——大约 80% 的时候是的。

[08:49] 信息在那里，Agent 也看见了，但它还是不会用。

[08:52] 历史 SQL 有价值，麻烦在历史 SQL 里混着太多杂质：最终版、临时分析、部门特殊口径、废弃表、以及私下修补过的查询。

[08:59] 一个新问题来了，Agent 可能搜到一条很像的历史 SQL，但它不知道这条到底是正确先例还是过期先例。

[09:05] 所以评价不再访问全量，也不再资料数量而在结构。

[09:08] 历史 SQL 可以当原料，不能直接当真相来源。

[09:11] 更有效的做法是把历史 SQL，中流程结构化的领域参考文档和可复用分析模式。

[09:16] 不是让 Claude 直接读一千条 SQL，而是让数据专家从里面总结：增长分析常用哪些表，留存分析标准口径是什么，漏斗分析要排除哪些异常，哪些历史字段已经废弃。

[09:23] 这个 SQL 文件最终版、草稿、不完整版混在一起，新人不能随便翻一个就拿去汇报。

## 第三层：Skills

[09:35] 接下来第三层是 Skills。

[09:36] 前两层告诉 Claude 哪些来源可信，第三层把 Data Agent 的执行路线写下来：先澄清什么，先查哪里，什么时候不能直接写 SQL，答案完成前怎么复核。

[09:45] 他们做过对比：没有 Skills，Claude 回答分析问题的准确率最高不超过 21%。

[09:49] 加上 Skills 之后，整体稳定超过 95%，一些领域接近 99%。

[09:53] 这个跳跃说明：卡点不止在 SQL 写得好不好。

[09:56] 卡住 Claude 的是它不知道先查哪里，不知道哪些表不能用，不知道哪些指标有特殊口径，不知道遇到歧义要问，也不知道答案完成前要验证什么。

[10:04] Anthropic 的做法是把这些经验拆成一个 Skill。

### 知识 Skill

[10:06] 第一个叫知识 Skill。

[10:08] 它更像一个顶层路由器，不会把所有知识一次性塞给 Agent，而是先让 Agent 查语义层。

[10:13] 如果语义层没有覆盖，它再从大约 30 个参考文件里加载当前领域最相关的表、连接方式和坑点。

[10:19] 比如用户问新用户留存，知识 Skill 会先让 Claude 查语义层有没有留存指标。

[10:22] 如果没有，再看留存参考文档。

[10:24] 如果问题涉及渠道，再看获客参考文档。

[10:26] 如果还涉及付费转化，再看收入参考文档。

[10:29] 这一步是在防检索失败——搜索范围从整个数据仓库缩小到几十个精选参考文件，Claude 才不容易迷路。

### 流程 Skill

[10:35] 第二个叫流程 Skill。

[10:36] 它规定的是资深分析师的工作顺序：先澄清问题，再通过知识 Skill 找来源，跑查询，最后让对抗审查 Agent 检查结果。

[10:43] 里面还打包了十几个可复用分析模式，比如留存曲线、比率分解、漏斗分析。

[10:48] 常见请求不用每次重新发明轮子。

[10:50] 所以知识 Skill 解决去哪找知识，流程 Skill 解决怎么完成分析。一个管路由，一个管步骤。

### 参考文档的结构

[10:55] 给 Agent 看的参考文档，也不能只写表名和字段名。

[10:58] Anthropic 的文档骨架包括：业务上下文、实体粒度、标准过滤条件、各张表的用法和不该用的场景、坑点以及显式的路由出发条件。

[11:05] 这几个词可以拆开听：

[11:07] **实体粒度**就是一行数据代表什么——是一行一个用户，一行一个订单，还是一行一个用户每天的行为？

[11:12] 如果 Claude 把一行一个用户每天的行为当成一行一个用户去计数，同一个用户就会被重复算很多次。

[11:17] **标准过滤条件**就是这类分析默认要排除什么——比如内部账号、测试账号、欺诈流量、退款订单。

[11:23] **坑点**就是资深分析师知道但新人不知道的东西——比如某张表名字看起来像用户表，但其实只覆盖某个实验；某个字段看起来像活跃标记，但历史上改过含义；某个分析必须排除欺诈流量。

[11:34] **路由出发条件**是告诉 Claude 遇到哪类问题该看哪套资料——比如问题里出现"实验"就先看原始事件，问题里出现"留存"就先看留存参考文档，涉及"渠道"再看获客文档。

[11:44] 这些内容不是死板 Skill 的拆谱，而是把选择原则、使用边界和容易踩坑的地方写清楚。

[11:49] 资深分析师脑子里的经验，新人没有，Claude 也没有。

[11:52] Anthropic 要做的，就是把这种经验写进 Data Agent 的工作路线里。

### Skills 的维护

[11:55] Skills 写完之后，关键转到维护。

[11:57] 数据模型每天都在变，如果不主动更新，Skills 文档几周内就会出错。

[12:01] Anthropic 自己吃过这个亏：上线时离线准确率大约 95%，一个月后掉到大约 65%。

[12:07] Skills 写了这张表该怎么用，但如果表结构、指标口径、看板定义每天都在变，Skills 不跟着变，它就会从导航变成旧地图。

[12:14] 后来它们把 Skills 文档和转换模型放在同一个仓库里。

[12:17] 改报表模型的 PR 如果没有碰 Skills 文件，审查规则会拦住。

[12:20] 现在大约 90% 的数据模型 PR 会同时包含 Skills 变更。

[12:24] 它们还会定期修剪 Skills 脚手架，因为模型升级后旧的失败模式可能不再需要提示。

[12:29] Skills 像地图，城市每天都在变，地图不更新，再好的司机也会开错路。

[12:34] 一致性也要一起管。

[12:35] 同一个 Skills 要在 Skills IDE、满工具、独立 Agent 里给出同样的答案。

[12:39] Anthropic 用一个统一来源，改动后自动同步到不同入口，避免每个界面都有自己的一套硬编码逻辑。

[12:44] 不同入口给出不同答案，会很快摧毁用户信任。

### 业务问题示例：知识 Skill + 流程 Skill 协作

[12:47] 再回到我们的业务问题。

[12:49] 这时知识 Skill 先路由到语义层，如果有高价值用户留存这个指标，就直接查询。

[12:54] 如果没有，它会加载这个领域的参考文档，找到正确的表、连接方式和过滤条件。

[12:58] 然后流程 Skill 接手：按流程确定时间窗口和用户分群，写好查询，再让对抗审查 Agent 检查逻辑有没有问题。

[13:04] 整条执行路径是被 Skills 规定好的。

[13:06] Agent 可以执行和推理，但不再从零开始自由发挥。

## 第四层：验证（Validation）

[13:09] 最后一层叫验证，Validation。

[13:11] 它是质量闭环，用来发现哪些失败模式还在漏。

[13:14] 前面三层大功告成以后，系统还是可能错。

[13:16] 数据整理好了，来源也分了信任等级，Skills 也写了流程，但这不等于 Claude 每次都真的答对。

[13:22] 验证这一层回答的就是：你怎么知道它没有只是看起来很对？

[13:25] 它要持续追问：错在哪类问题，哪个 Skills 版本变好了，哪个改动没用，线上用户正在纠正什么，有没有答案看起来合理但实际错了。

### 离线评测

[13:33] 上线前靠离线评测。

[13:34] 离线评测就是在 Agent 正式交给业务方之前，先准备一批有标准答案的问题，让它反复考试。

[13:39] 不能随便问几个问题试试看，要把每个领域常见、罕见、容易出错的问题都放进去。

[13:44] 你可以把它想成自动驾驶的测试场：车能跑不代表跑得对，数据 Agent 能生成答案也不代表答案可靠。

[13:50] 离线评测至少要告诉你：收入类问题是不是都对，留存类问题是不是经常错，实验分析是不是完全不会，涉及时区是不是容易出问题。

[13:57] 一测出来，你才知道该改哪个 Skills、哪个文档、哪个指标定义。

### 评测题的三个来源

[14:00] Anthropic 的评测题来自几个方向：

[14:02] **第一类是基于看板的常见问题**：由 Claude 自动生成，再由人验证。

[14:06] 比如公司有一个高管收入看板，上面有本月收入、环比增长、企业客户收入、退款率、地区分布。

[14:11] 这些看板可以生成一批业务常见常问的问题，再由人确认标准答案。

[14:15] **第二类是罕见问题**：把 Claude 接上业务上下文，让它生成一个领域里那些不那么常见但可能真实出现的问题。

[14:21] 罕见问题就是不一定在看板上，但业务真的可能问。

[14:24] 比如"Q2 新产品上线后，老客户中的高价值客户留存有没有变化"。

[14:28] 这种测试测的是 Claude 能不能处理边角问题，而非只会回答看板上的常规问题。

[14:32] **第三类来自用户纠正**：每次业务方在对话里纠正 Agent，这一轮纠正都会成为候选评测题。

[14:37] 如果用户说"你用错表了，这个问题应该看企业收入表"，这类纠正是宝贵失败案例。

[14:42] 用户纠正过的错，下一次要变成考试题，不能再错。

### 评测题的稳定性

[14:45] 评测题的答案必须稳定。

[14:47] 如果底层数字每天变，题目就会失效。

[14:49] 所以要锁定快照日期，或者让评分器检查查询逻辑，不要只看最终数值。

[14:53] 比如今天问"昨天收入是多少"，明天这个"昨天"就变了，后天数据回补数字也可能变。

[14:59] 如果标准答案跟着实时数据飘，你就不知道 Claude 是错了还是数据变了。

[15:04] 所以测试题必须锚定在稳定对象上。

### 评测结果的追踪

[15:06] 每次评测跑完，结果像遥测数据一样落进数仓表：Schema 版本、Gate SA、模型 ID、每条是否通过、Token 消耗、耗时。

[15:13] 评测结果不能只当一堆日志，还要像业务数据一样能被查询、能看趋势。

[15:16] 比如今天 96%，下周 94%，再下周 91%——单次看都不吓人，但趋势很危险。

[15:21] 他们还按领域设置上线门槛：某个领域的评测切片没达到阈值之前，不能向业务方发布 Agent。

[15:26] 早期这个阈值大约是 90%。

[15:28] 离线评测准确率要追求接近 100%。

[15:31] 这不保证线上不会错，但至少说明在覆盖范围内没有明显缺口。

[15:34] 评测题量也要算收益。

[15:36] Anthropic 发现每个主题几十个题之后，编辑收益会递减。

[15:39] 模型代际升级后，所需题量上限还可能降低。

[15:42] 为什么离线评测要接近 100%，90% 还不够？

[15:45] 因为离线评测本来就是你知道答案的考题。

[15:48] 如果这种题都错，线上真实问题只会更乱。

[15:51] 而且答对数字还不够，最好还走对路径。

[15:53] 如果它绕过官方语义层，自己写 SQL 碰巧算对了，这仍然不是理想状态。

### 消融实验

[15:57] 接下来是消融实验。

[15:59] 消融实验听起来学术，做法很简单：每次拿掉一个组件，看系统会不会明显变差。

[16:04] 如果拿掉以后准确率没变，这个组件可能没那么值。

[16:07] 如果拿掉以后准确率掉很多，它就值得保留。

[16:10] 每次只改一个组件，用固定评测集对比通过率，一小时内能替代大量争论。

[16:14] 比如要不要加一个审查子 Agent？A 版本没有审查，B 版本加审查其他都不变。

[16:19] 如果 B 准确率明显提高，就说明审查有用。如果没提高，就别为它付 Token 和延迟成本。

[16:24] 它们最有价值的一次消融反而是负结果——也就是前面说的，直接给 Agent 整个看板、转换模型、基本 SQL 全文，确认它确实读了，但准确率变化不到一个百分点。

[16:33] 再查混淆因素，发现 80% 的错误题答案就在语料里，Agent 还是没有用。

[16:37] 这个实验把路线图重新定向了好几个月。

[16:40] 结论很硬：评价不再更多信息，而在信息有没有被结构化地编排。

[16:44] 这句话对很多公司都很有用。

[16:46] 靠消融实验判断是不是应该给 Agent 更多资料——固定一套评测，只改一个变量，跑前后对比。

[16:51] 如果没有提升，哪怕这个想法听起来很合理，也不要继续加复杂度。

[16:54] 同时试过没用的办法也要记录下来。

[16:57] 比如继续把文档写长，可能会让文档更糟而不是更好，人觉得更完整，Claude 反而更难用。

### 上线后的验证手段

[17:02] 上线后还有一系列验证手段。

#### 对抗审查

[17:05] 第一个叫对抗审查。

[17:06] 它的做法是让另一个子 Agent 专门挑错：拆解最终答案里的所有假设——比如用了哪张表，过滤条件有没有漏，时间窗口是不是对，指标口径是不是一致。

[17:15] 在评测集里，对抗审查把准确率提高了 6%，代价也很明确：多花 32% Token，延迟增加 72%。

[17:21] 所以它不适合每个问题都开。高风险问题值得开，低风险问题不一定值得。

#### 来源追溯（Provenance Footer）

[17:24] 第二个叫来源追溯，Provenance Footer。

[17:27] 追溯会标明：答案来自语义层、精选参考还是原始表，底层数据有多新鲜，谁负责这个模型。

[17:33] 追溯不会让答案天然正确，但它会告诉用户这个数是从哪里来的，能信到什么程度。

[17:38] 比如追溯写"来源是原始表，新鲜度未知，负责人未知"，用户就知道这个答案最好不要直接拿去给老板。

[17:44] 如果追溯写"来源是语义层，数据更新到某一天，负责人是财务数据团队"，可信度就高很多。

#### 被动监控

[17:50] 第三个是被动监控。

[17:51] 它持续追踪两个生产信号：

[17:53] 一个是 Agent 的查询通过语义层解决的比例。如果这个比例下降，说明 Agent 可能越来越多地绕开官方路径。

[17:59] 另一个是回答中出现纠错语言的比例——比如"你用了错误的表"、"你漏了欺诈过滤条件"。

[18:04] 这类话一多，说明线上用户正在替系统发现错误。

[18:06] 这里监控的是具体失败类型，不是抽象的用户满意度。

[18:09] 如果越来越多查询绕过语义层，说明系统可能在退化，Claude 又开始自由写 SQL。

[18:14] 如果对话里越来越多出现"你用错表了"、"这个口径不对"，说明线上用户正在替系统做质检。

#### 主动纠错收集

[18:19] 第四个是主动纠错收集。

[18:21] 它更进一步：定时 Agent 每隔几小时扫描业务方频道，发现用户说"你用了错误的表"、"这个纠错语言"，就自动创建修复，写进对应参考文档，开 PR 给负责人。

[18:30] 这些纠错也会回流到离线评测集——线上犯过的错，会变成下一轮离线考试里的题。

[18:36] 这一步把纠错从聊天里的道歉变成系统被更新：线上被纠正一次，文档修一次，测试加一条以后防止再错。

### 未解决的失败模式：静默失败

[18:42] 不过 Anthropic 坦诚地指出，还有一种失败模式没有完全解决：静默失败（Silent Failure）。

[18:47] 答案错了，看起来合理，没人指出来。

[18:54] 他们对关键指标做渐进性检查，但明确说还没有稳健方案。

[18:59] 这个边界让 Anthropic 保持克制——没有把数据 Agent 正确性讲成已经完全解决。

## 完整示例：四层串联

[19:03] 最后用一个普通业务问题，把四层完整串起来。

[19:06] "上周我们的付费用户增长怎么样？"

[19:08] 这句话看起来简单，但里面有很多口径：付费用户怎么算，退款算不算，测试账号排不排除，上周是自然周还是最近 7 天，数据更新到哪天。

[19:16] 如果直接把它交给一个模型单独回答，它很容易变成自由发挥。

[19:20] 在 Anthropic 这套系统里，它会被四层接住：

[19:22] **第一层数据基础**先保证付费用户有官方定义和官方表。这一步不让 Claude 在一堆相似表里猜，也不让它自己决定退款、测试账号、内部账号到底算不算。

[19:31] **第二层可信来源**告诉 Claude 先查语义层里的官方指标。如果语义层里已经有付费用户或周付费用户指标，它就直接走这条官方路。

[19:37] 如果没有，再研究血缘图、参考文档和业务上下文，找最接近官方口径的来源。

[19:42] **第三层 Skills** 规定它具体怎么做：先确认时间窗口和过滤条件，再查询，再写清来源和限制。如果问题涉及收入、留存、渠道，就加载对应参考文档，而不是在全公司数据仓库里乱搜。

[19:54] **第四层验证**检查它有没有走官方路径，数据是不是新鲜，结果能不能和看板对齐。

[19:59] 如果用户后来指出漏了退款过滤，这个纠错还会回到文档和测试里，下次变成一道评测题。

[20:04] 所以这个问题由整套系统共同回答：它建立在干净的数据基础里，把付费用户压到官方定义，再由语义层或血缘图定位来源，Skills 规定查找、查询、审查的流程，离线评测确保覆盖范围内没有明显缺口，上线后追溯监控和纠错机制继续兜底。

[20:17] 四层合在一起是一套答案治理系统。

## 总结

[20:19] Anthropic 的数据 Agent 能准并不是因为 Claude 可以更自由地查数仓。

[20:23] 系统先把正确答案空间一步步收窄：路由、执行、验证。

[20:26] 所以这一期收在一条核心规则上：

[20:28] 企业要做数据 Agent，不要一开始就对资料和权限。

[20:31] 先画出你的答案路径：把公司里每个关键概念的官方来源定下来，把去哪里找、怎么问、怎么验证的流程写清楚，再让 Agent 沿这条路径工作。

[20:38] 这比指望模型自己变聪明要可靠得多。

[20:41] 这一期我们先把四层架构讲清楚。

[20:43] 下期我们继续往下看：如果一家公司不是 Anthropic，没有这么完整的数据系统，应该从哪里开始？

[20:48] 原文给了一个很务实的小版本：少量官方数据集、基础语义层、离线评测，再加一个薄的 Knowledge Skill。

[20:53] 也就是先别急着造一个全能数据 Agent，先把最常问、最容易错、最值得治理的那几条答案路径跑通。
