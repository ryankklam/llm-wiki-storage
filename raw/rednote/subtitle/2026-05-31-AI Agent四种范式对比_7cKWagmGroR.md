## 常见误区

[00:54] 那怎么拆解呢？我们先从最常见的误区说起。
[00:58] 很多人默认以为这四种是线性进化关系：
[01:01] Tool Use 最简单，ReAct 高级一点，
[01:04] Plan-and-Execute 更高级，
[01:06] Multi-Agent 最牛。
[01:08] 这是面试中最大的坑。
[01:10] 实际上他们根本不是同一维度的比较对象。

## 四层架构解析

[01:12] Tool Use 是基础能力层，决定模型能不能调用外部工具。
[01:17] ReAct 是推理框架层，
[01:20] 定义推理和行动怎么交替。
[01:22] Plan-and-Execute 是控制流程层，
[01:24] 规定先规划还是边想边做。
[01:27] Multi-Agent 是组织架构层，
[01:30] 关心多个 Agent 怎么协作。
[01:33] 四层可以叠加而不是互斥。
[01:35] AutoGen 里的一个 Agent 就可以同时用 ReAct、Function Calling，
[01:41] 整体又是 Multi-Agent 架构。
[01:43] 清楚了层次关系，回答才不会跑偏。

## 关键认知

[01:46] 这就引出了关键认知：
[01:47] 选型不是四选一，
[01:49] 而是根据场景在每一层做组合决策。

## 各层选型分析

### Tool Use 层

[01:52] 那每一层怎么选呢？先说 Tool Use 这一层。
[01:55] 模型根据上下文自主决定要不要调工具、调哪个、传什么参数，
[02:00] 拿到结果后继续回复。
[02:03] 优势是延迟低、架构简单。
[02:05] 但面对多步推理，每一步独立决策，
[02:09] 缺少全局规划容易偏离目标。
[02:12] 所以它最适合单一或简单调用，
[02:14] 比如查天气、发邮件这类确定型操作。

### ReAct 范式

[02:17] 当问题来了，如果任务不只是调一两个工具，
[02:20] 这就引出了 ReAct 范式。
[02:22] 核心是推理和行动交织进行，
[02:25] 格式是 Thought、Action、Observation 三段循环：
[02:28] 先思考下一步做什么，
[02:30] 执行动作，拿到观察结果再继续思考。
[02:33] 最大价值是可解释性，
[02:35] 打开日志能看到每一步的决策路径。
[02:38] 代价是延迟，每多轮循环就多一次 LLM 调用。
[02:43] 适合中等复杂度且对可观测性要求高的任务，
[02:47] 比如客服工单、数据分析。

### Plan-and-Execute 范式

[02:49] 但 ReAct 解决不了一个更深的问题：
[02:52] 任务如果需要十几步，
[02:54] 光靠边想边做不仅慢，而且容易迷失方向。
[02:58] 怎么办？
[02:59] 这就引出了 Plan-and-Execute 范式。
[03:01] 理念是先规划再执行，
[03:04] 模型在动手前生成完整计划，
[03:07] 然后逐步执行。
[03:08] 这解决了 ReAct 缺乏全局视野的弱点。
[03:11] 代价是规划消耗推理资源，
[03:14] 计划可能不准确。
[03:15] 好的实践是在执行中引入重新规划机制。
[03:18] 适合步骤多但结构清晰的任务，
[03:21] 比如大型代码重构、复杂数据处理流水线。

### Multi-Agent 范式

[03:24] 但还有一个更棘手的问题：
[03:25] 如果任务复杂度已经超过单个 Agent 的能力边界了？
[03:30] 这就引出了 Multi-Agent 多智能体范式。
[03:34] 思路是把复杂任务拆给多个专门 Agent，
[03:38] 每个有自己的角色、工具和知识范围，
[03:41] 通过消息或共享状态协作。
[03:44] 最大好处是职责分离，
[03:46] 每个 Agent 的 Context Window 只需关注自己的范围。
[03:50] 主流框架如 AutoGen 和 CrewAI，
[03:53] 通过编排多个 Agent 解决协作问题。
[03:55] 适合角色边界清晰的协作场景，
[03:58] 比如软件工程的多角色配合、内容编审发布流程。

## 技术选型框架

[04:02] 好，四种范式讲完了。
[04:03] 面试官很可能会追问一个深化问题：
[04:06] 技术选型的优先级怎么排？

[04:09] 这里给一个实用框架：

**第一看任务复杂度：**
[04:10] 单步或少量调用，直接用 Tool Use；
[04:13] 多步推理加可解释性，上 ReAct；
[04:17] 步骤多且结构化高，用 Plan-and-Execute；
[04:20] 只有角色天然分离或单 Agent 上下文装不下时，
[04:25] 才上 Multi-Agent。

**第二看延迟敏感度：**
[04:26] 实时交互，优先 Tool Use 或最简 ReAct；
[04:32] 后台批处理，充分发挥后两者优势。

**第三看可观测性需求：**
[04:36] ReAct 的循环是天然审计追踪；
[04:39] Multi-Agent 需同时追踪多 Agent 的状态，
[04:45] 排查难度最高。

## 核心原则

[04:47] 说到底，技术选型的核心不是找最好的范式，
[04:50] 而是用最少的复杂度解决当前问题。
[04:53] 范式越高级，系统复杂度越高，
[04:56] 复杂度本身就是成本。

## 面试回答模板

[04:58] 面试时你可以这样回答：

[05:00] AI Agent 的四种范式并不是同层级对比对象：
[05:03] Tool Use 是基础能力层，决定 Agent 能否调用工具；
[05:08] ReAct 是推理框架层，通过思考与行动循环赋予可解释性；
[05:14] Plan-and-Execute 是控制流程层，通过先规划后执行保证全局视野；
[05:21] Multi-Agent 是组织架构层，通过角色分离应对超复杂任务。

[05:26] 选型上按任务复杂度、延迟敏感度和可观测性三个维度决策，
[05:32] 从最简单的 Tool Use 开始逐步叠加，
[05:35] 原则是用最少复杂度解决当前问题。
