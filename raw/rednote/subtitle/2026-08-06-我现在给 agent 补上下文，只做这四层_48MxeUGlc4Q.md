# 我现在给 agent 补上下文，只做这四层

**来源**: [小红书](http://xhslink.cn/o/48MxeUGlc4Q)
**时长**: 约7分27秒

---

## 核心观点

**上下文不是给模型补充更多知识，而是给他当前决策所需要的真实事实。**

给 Agent 补上下文，不再追求"给的更多"，而是追求在当前任务里，能不能让它找到真正有效的信息。上下文系统不是让 Agent 每次都读得更多，而是让它每次只读对的东西。

---

## 重新定义上下文

[00:00] 上一期我提到我现在优化 Agent 主要是做四件事，第一件就是给 Agent 补充真实的上下文。这期我想具体聊聊，我现在到底是怎么做的。

[00:15] 很多人一提到给 Agent 补上下文，第一反应就是把 Agent 的 Prompt 写更长一点，把公司的文档全部塞进知识库，然后再接一个 RAG，让 Agent 什么都能搜到。以前我也是这么理解的。

[00:30] 但做了一段时间以后发现了一个很现实的问题：Agent 能看到的资料越来越多，并不意味着理解越来越准确。有时候上下文越多，规则越多，历史规则越多，互相冲突的内容越多，Agent 最终可能拿着一堆资料，却没有拿到当前任务真正需要的那个事实。

## 一个典型问题：日期处理

[01:00] 我之前遇到过一个很典型的问题。Agent 帮我完成了一次代码修改，从代码层面看没有任何问题——服务能够启动，测试也没有报错，三角测试也都通过了。

[01:20] 但我后面真正核对运行结果时，发现它选错了应用日期。代码写的功能也执行成功了，但运行结果是错的。

[01:35] 这件事让我意识到，模型并不是不会写日期处理逻辑，它缺的是另外一些东西：

- **现在准确是什么时间**？使用的是哪个时区？
- 这里说的"今天"到底是自然日，还是门店的上一个营业日？
- 凌晨两点之前的数据属于今天，还是前一天？
- 节假日有没有特殊规则？
- **历史代码的逻辑实现才是当前真正有效的口径**

[02:10] 这些信息不会因为模型能力升级，就自动出现在模型的脑子里。这也让我重新定义了什么叫上下文。

## 上下文的四层架构

[02:25] 上下文不是给模型补充更多知识，而是给它当前决策所需要的真实事实。即使这个事实很小。我现在大概把 Agent 的上下文分成了四层。

### 第一层：项目地图（AGENTS.md）

[02:40] 第一层，AGENTS.md，负责提供项目地图。

[02:50] 以前我的 AGENTS.md 很像一本操作手册，里面会写：开始任务前先分析、修改代码前先搜索相关文件、完成后一定要执行测试、不要修改无关代码、最后要总结修改内容和风险。

[03:10] 这些要求当然没有错。但是随着模型变强，我发现其中很多内容已经没有必要写得这么详细。模型本身已经知道要测试、要搜索。

[03:25] 所以现在 AGENTS.md 我精简了，它更像一张地图，而不是一本手册。它只回答三个问题：
1. **项目是什么**——核心业务、技术栈、架构概要
2. **重要信息在哪里**——配置在哪、日志在哪、关键文档在哪
3. **有哪些不能违反的业务边界**——红线规则

### 第二层：按需知识

[03:50] 第二层，按需知识。

[03:55] 把会议纪要、历史决策、业务规则和排查经验，整理成可以逐层查询的知识树。

[04:05] 不是一次性全部塞给 Agent，而是让 Agent 知道有这么一棵知识树存在。当任务需要某一块知识的时候，它会主动去查询对应的分支。

[04:20] 比如说任务涉及到了支付模块，Agent 会去查支付相关的业务规则；任务涉及到了库存，它会去查库存的排查经验。按需加载，不是按量加载。

### 第三层：任务现场

[04:40] 第三层，任务现场。

[04:45] 在每次任务开始时，动态组装当前 Issue、相关代码、业务口径、准确时间、环境和日志状态。

[04:55] 这一层是最关键的。因为前面的两层都是相对静态的，而任务现场是每次任务都不一样的。Agent 需要知道：
- 当前 Issue 是什么
- 相关的代码文件是哪些
- 这个功能对应的业务口径是什么
- 现在准确的时间是什么（时区、营业日定义）
- 运行环境是什么
- 最近的日志状态如何

### 第四层：长期记忆

[05:30] 第四层，长期记忆。

[05:35] 只留下稳定的结论、决策、风险和验证结果，而不是把所有历史过程都永久保留。

[05:45] 这份记忆也不是全部记忆下来的对话，而是先沉淀进知识库，等未来遇到相关问题时，再按需加载。

[05:55] 好的记忆不是什么都记住，而是知道什么值得留下，以及什么时候重新拿出来。

## 总结

[06:10] 所以我现在给 Agent 补上下文，主要分成四层：

| 层级 | 名称 | 核心职责 |
|------|------|----------|
| 第一层 | **项目地图** | 通过精简后的 AGENTS.md，告诉 Agent 项目是什么，重要信息在哪里，有哪些不能违反的业务边界 |
| 第二层 | **按需知识** | 把会议纪要、历史决策、业务规则和排查经验，整理成可以逐层查询的知识树 |
| 第三层 | **任务现场** | 在每次任务开始时，动态组装当前 Issue、相关代码、业务口径、准确时间、环境和日志状态 |
| 第四层 | **长期记忆** | 只留下稳定的结论、决策、风险和验证结果，而不是把所有历史过程都永久保留 |

[06:50] 给 Agent 补上下文，已经不是给它写一份越来越长的说明书，而是让它知道：
- 自己现在在哪里
- 正在处理什么问题
- 应该去哪里寻找事实
- 哪些经验值得在下一次继续使用

[07:10] 真正好的上下文系统，不是让 Agent 每次都读得更多，而是让它每次只读对的东西。

[07:20] 上下文解决了 Agent 知道什么。但知道还不够，它还需要真正进入我们的业务系统完成操作。下一期我会继续聊第二件事——我是怎么把人工操作转化为 Agent 可以持续执行的任务工具。

## 关键概念总结

| 概念 | 含义 |
|------|------|
| **四层上下文架构** | 项目地图 + 按需知识 + 任务现场 + 长期记忆 |
| **上下文 ≠ 更多知识** | 上下文是当前决策所需要的真实事实 |
| **AGENTS.md 精简化** | 从操作手册变为项目地图，只回答三个问题 |
| **按需知识树** | 知识分层组织，Agent 按任务需要查询对应分支 |
| **任务现场动态组装** | 每次任务开始时动态组装 Issue、代码、口径、时间、环境、日志 |
| **长期记忆筛选** | 只保留稳定的结论、决策、风险和验证结果 |
