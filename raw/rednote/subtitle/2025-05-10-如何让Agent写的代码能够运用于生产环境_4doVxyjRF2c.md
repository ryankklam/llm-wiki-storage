# 如何让Agent写的代码能够运用于生产环境

## 背景

今天聊一个很多人都在问的问题：怎么让AI写出来的代码真的能**上线**？

你可能已经用了很多代码**Agent**来写项目，体感上确实快了。但如果你在一个真实的企业级项目里，面对十几万行代码、RPC框架、流程引擎、配置中心、分布式缓存——全套中间件，你大概率遇到过这个情况：**Agent写出来的代码语法完美、风格统一，但业务逻辑有微妙的错误。**

这种错误在编译层面没问题，但是实际运行却**错谬百出**。为了修这些错误形成恶性循环，不仅耗费金钱，还让代码仓库变成了一座**屎山**。

比如：
- **架构自断**：用了 `Double` 而不是 `Long`，单位搞错了
- **链路遗漏**：改了主链路，但漏了国际化链路的同步修改
- **健壮性缺失**：调用外部服务没设超时和降级

这些错误有一个共同特点：**它们不是模型不够聪明导致的**。模型的单步推理能力已经很强了，问题出在模型**不知道**你项目里那些从来没被写下来的规矩。

今天分享一下阿里团队的一个实践：他们在一个存量代码项目上，用一周时间搭了一套**Harness体系**，把AI代码采纳率从25%拉到了90%。不是换了更强的模型，仅仅是根据 **Harness Engineering** 的定义，搭了一套外部的约束和反馈系统。

## AI工程实践的三次范式迁移

AI工程实践正在经历第三次**范式迁移**：

| 阶段 | 名称 | 时间 | 核心 |
|------|------|------|------|
| 第一次 | **Prompt Engineering** | 2020-2024年 | 怎么写好一条指令（Few-Shot、Chain of Thought、角色设定），优化单次交互 |
| 第二次 | **Context Engineering** | 2025年 | 给Agent看什么，动态构建上下文窗口（Agentic RAG、检索工具定义）。Substack CEO 的比喻是"给邮件附上所有正确的附件" |
| 第三次 | **Harness Engineering** | 2026年 | 设计跨越多个会话、多个Agent角色、多个执行阶段的完整系统架构 |

本质上来说，由于大模型的不确定性，每次你发现Agent犯了一个错误，你就需要花时间**工程化地消除它再次发生的可能性**。

注意：不是Show Prompt、不是加一句"请注意不要犯这个错"，是**工程化的消除**——意思是你要把这个约束变成一个文件、一条规则、一个自动化检查，让它成为系统的一部分，而不是一次性的口头叮嘱。

## Agent的四种典型失败模式

为什么需要这么做？因为Agent有四种典型的失败模式：

### 1. 试图一步到位

拿到复杂需求后，Agent倾向于在一个上下文窗口里完成所有工作。**上下文填充率超过40%之后，输出质量快速衰退**，开始出现幻觉循环、输出格式错误的工具调用。

### 2. 过早宣布胜利

Agent完成部分工作就说"编码完成"，但实际上编译都过不了。

### 3. 没做端到端验证就标记完成

Agent认为功能实现了，但没跑过完整的测试，部署之后才发现关键链路不通。

### 4. 冷启动问题

每次新会话都要花大量Token重新理解项目结构，真正用于编码的预算被严重挤压。

这四种失败模式的共同根源是：**Agent缺乏外部的结构化约束和反馈机制**。

Anthropic 在他们的工程博客里说得很直白：**Agent无法准确评估自身产出的质量，你不能指望Agent自己审查自己。**

## 实操：搭建Harness体系

### 整体架构

在项目根目录下建一个 `.harness` 目录，里面放四样东西：**规则、技能、知识库、变更记录**。

```
.harness/
├── rules/           # 规则体系
├── skills/          # 技能体系
├── knowledge/       # 知识库
└── changes/         # 变更记录
```

### 一、规则体系（3份文件）

- **工程结构规范**：项目分几个模块，每个模块的职责是什么，分层架构是 Controller → Service → Domain → Repository → Adapter 五层
- **开发流程规范**：开发流程、PR规范
- **项目编码规范**：
  - 金额字段必须用**浪花型**（BigDecimal），单位为分，禁止 `Double` 和 `Float`
  - 外部服务调用必须设超时和降级
  - 流程编排组件内不写大段业务逻辑，必须委托 Service 处理

这些规则的特点是：**它们不在代码里，但所有资深开发者都知道**。以前靠口头传承，现在写成文件让Agent也能知道。本质上讲，就是给Agent看详细的文档进行**软约束**。

### 二、技能体系（9个Skill）

每个Skill是一份结构化的SOP。

最核心的是 **CodingSkill**，里面有八份分层编码规范，从Controller到Domain到Adapter，每一层怎么写都有明确的模板和约束。Agent编码的时候不是凭感觉写，是按规范一层一层实现。

另一个关键Skill是 **Expert Reviewer**，这是一个评审Skill，它定义了两种评审循环：
- **计划评审**（Plan Review）
- **执行评审**（Execution Review）

每条评审意见必须包含：问题描述、修改建议和优先级。

还有一个 **UnitTest Skill**，体现了**改动驱动测试**原则：改了哪个接口就测哪个接口，不是一刀切测全部，而且要求优先用线上真实请求的出入参来构造测试数据。

### 三、知识库

放在项目根目录的 `wiki` 文件夹里，列目录树、数据模型、核心业务流程。这些是Agent理解业务上下文的素材。

但注意：**知识库不会主动加载到上下文里**，Agent根据任务需要自主查阅。这是**按需获取**，不是全量灌入。

### 四、变更管理

每个需求创建独立目录，从需求分析文档、任务拆分清单、编码报告、评审记录、CI结果到部署验证，全流程留痕。评审文件用版本递增，版本永远只增不减。

## 效果数据

搭完这套体系之后的效果：

| 指标 | 之前 | 之后 |
|------|------|------|
| AI代码采纳率 | 25% | **90%** |
| 首次编译通过率 | 低 | 显著提升 |
| 关键链路缺陷 | 频发 | 大幅减少 |

## 核心要点总结

1. **不要指望换更强的模型来解决工程问题**——问题不在模型能力，在于缺乏外部约束
2. **规则体系**：把隐性知识显性化，让Agent知道项目规矩
3. **技能体系**：用结构化SOP替代自由发挥，规范Agent的每一步操作
4. **知识库**：按需获取，不是全量灌入
5. **变更管理**：全流程留痕，可追溯、可审计
6. **评审循环**：Agent不能自己审查自己，必须引入外部结构化反馈

> 关键理念：每次发现Agent犯错，就工程化地消除它再次发生的可能性——把约束变成文件、规则和自动化检查，而不是一次性Prompt。
