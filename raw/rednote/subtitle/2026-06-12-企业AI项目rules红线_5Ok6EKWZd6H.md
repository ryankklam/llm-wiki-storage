## 二、rules.md 的本质与常见错误

### 2.1 rules.md 是什么

[00:38] 那 rules.md 到底是什么？说人话，就是你立给 AI 的项目规则文件。它干每件事都要先服从这一份。

[00:44] Claude Code 的 CLAUDE.md，Cursor 的 Cursor Rules，不管哪个工具，本质都是同一份东西。

### 2.2 两种最常见的错误写法

[00:49] 听着简单，可大多数人写出来的规则根本不管用。两种最常见的写法，我挨个给你拆。

**第一种：写得模糊**

[00:54] "代码要优雅"、"性能要好"——好算好，AI 自己猜。你后面反攻三轮，攻击基本就保不住了。

**第二种：只写要做什么，不写绝对不做什**

[01:05] 这才是最要命的。没有红线的 rules.md 等于没 rules.md。OpenAI、Claude、Cursor 都一样，没卡红线，代码越写越容易崩。到 Code Review 哪天才发现一堆动了不该动的地方。

### 2.3 反直觉的坑：不是写得越多越好

[01:19] 还有一个反直觉的坑：不是写得越多越好。写太长，AI 反而漏掉关键那条。你以为写得越宽越保险，结果最该守的反而漏了。

## 三、五条硬规矩

[01:27] 那一份能用的 rules.md 该长什么样？两套东西：五条硬规矩 + 六个写法门道，全压在一份 Markdown 文档里。

[01:35] 五条硬规矩里先说四条你必须立：

### 3.1 第一条：先写清这个项目不是什么

[01:37] 第一条，先写清这个项目不是什么、不做哪类活。一在文档最前面，比写一百条要做什么都管用。

### 3.2 第二条：每条规则要能量化、能验证

[01:44] 第二条，每条规则要能量化、能验证，还要附一个"为什么"。AI 知道为什么，才会真正按规则走。这条跟你带团队是一个道理。

### 3.3 第三条：核心规则做和不做都列清楚

[01:53] 第三条，核心规则做和不做都列清楚，不留模糊地带。

### 3.4 第四条：技术栈不写名字，写具体版本号

[01:57] 第四条，技术栈不写名字，写具体版本号。不写版本号，AI 会自己挑一个最新的，踩过坑的人都懂。依赖冲突一冒头，回滚就是一个通宵。

### 3.5 第五条：整份文档压在五百字以内

[02:05] 第五条，整份文档压在五百字以内。超过这个字数，AI 漏掉关键项的概率明显上升。

---

## 四、六个写法门道

[02:11] 六个写法门道里最关键的两条：

### 4.1 禁止项优先

[02:14] 第一条，禁止项优先。先告诉 AI 别做什么，比告诉它做什么更管用。

### 4.2 给理由不能只甩"不许这么写"

[02:19] 第二条，给理由不能只甩"不许这么写"，要把背后的原因写出来。AI 知道为什么，比单纯被你管着听话得多。

[21:55] OK，我们现在已经切换回了这样一个模式，那基本上我们就已经把 Specate 在我们这个当前项目的一个配置，已经全部都做完了。

[22:08] 那如果是回到我们当时给大家讲这个 OpenSpec，它在去进行做的时候，我们在开始项目之前所需要的是我们去确定一下它的 Config 点压没有文件。那对于这个 Specate 来说，我们所需要做的就是来完成项目之前去配置它的 Constitution，也就是确定一下它的项目宪法。

[22:36] 那么这个项目宪法呢，其实非常非常关键，而且我们能够看到，对于这个项目宪法，它默认在 Specate 下面的 Memory 里面的 Constitution 的 Constitution.md 文件里面，它其实只是给了我们这样的一个架构体系，它并没有去给我们生成一些什么所谓的实质的内容。所以证据这个针对于宪法，我们要结合着自己的实际的项目，来去进行经验系统。

[23:03] 你在最开始的时候，可以先按照一些规范，来去生成它的一个基础的版本。然后随着你不断的像这个深入要不断的去维护，一个项目的宪法，这个是一定需要准备的。那我们在最开始去进行构建的时候，肯定是没有办法一步到位，把所有的可能的这些宪法，把所有可能的这些边界条件，都给写清楚。但是没有关系，我们有一套基本的这样一个标准规范，能够在最开始的时候，去进行一些约束。后面哪怕是去增加一些新的功能，在当前的这样一个技术架构和规范模块之下，其实你只需要去新增它，每一个模块下面小的一些功能点，或者是细节点就可以了。

[23:47] 那都有什么呢？

#### 6.6.1 AI 行为边界

[23:48] 首先第一个就是我们在 Constitution 下面，可以去明确的去确定一下当前在项目开发过程中，它的一个 AI 行为的边界。能做什么，不能不能做什么。

#### 6.6.2 禁止项必须写死

[24:01] 那么第二个就是一定要把对应的这个禁止项给写死。我一直在强调，大模型的显示它的这个发散能力是很强的。你如果不给它把它写死的话，它会给你额外的去写很多的这个蛋嘛，写一些那些八道的东西。这个都是可能值，都是可以可能的。所以我们把禁止项给它写死这样的话，它在每次执行的时候，都会遵循这个 Constitution，它的一个项目的约定。

#### 6.6.3 技术细节落地

[24:26] 那么第三个我们是可以在 Constitution 里面，去把每一步可能存在的一些纠片，去给它落地成一些技术的细节。

#### 6.6.4 代码复用的重视

[24:36] 以及非常非常关键的就是，我们一定要强调一下关于代码复用的重视。你在我当前的项目中是怎么做的。因为 AI 当作写了，无论是哪一个模型，Claude 还是这个 Codex，他们其实更喜欢新去创建代码，而不是更喜欢去复用现有的代码。这个是他们一直以来存在的这样一个问题。

### 6.7 五条铁律与六原则

[25:01] 所以关于这个好的 Constitution 或者是坏的 Constitution，他们之间的一个区别是什么呢？大家可以遵循这样一个体验出了五个比较铁率：

#### 铁律一：先告诉 AI 我不是什么

[25:12] 那么第一个就是一定要去告诉他，我不是什么。也就是一定要去划定一下，你当前用户的电影，当前的项目的范围。

#### 铁律二：可量化、可验证的规范 + 原因

[25:21] 那么第二个一定要在里面去做一些可量化的可验证的一些规范，以及你在每条的约束下面，可以去给它添加一些原因。比如说我为什么要用这个框架，我为什么不用另一条技术栈，我为什么要这样命名定义。你可以去给它写一些原因，或者是一些代码定义这样的话，AI 就知道了，它才会真正的去进行一个遵循。这个其实算是一个比较微妙的这样一个优化点，我们在实测的过程中发现是比较有用的。

#### 铁律三：核心标记，做和不做都列清楚

[25:56] 那么第三个就是一定要去做一些核心的标记，让它做什么，以及不做什么。比如像我们在使用 OpenSpec，再给它确定 Configure 的 yaml 文件的时候，我们说有一条红线，这个红线我们让你不做的，你一定要去禁止做。

#### 铁律四：技术栈写具体版本号

[26:12] 然后还有一个就是我们可以在它的项目的宪法里面去明确的标示一下，我们当前所用的这个技术栈，它所使用的具体的这样一个版本。因为不同的这个版本它的语法，不同的这个版本它的语法，它的一些接口的兼容都是不一样的。比如你这个 Python 9 你和 Python 12，它在很多的这个语法就不一样。如果你把对应的这个技术栈版本写在里面，那么它在进行执行的时候，会先看你当前这个宪法，去找和写你对应的这个版本所兼容的这样一个规范。就会导致它生成出来的这个代码，不会存在太大的这样一个兼容问题。

#### 铁律五：文档长度控制在 500 字以内

[26:55] 那么爹坏的毫无疑问，这个大家应该是比较容易能够看。一个是比较模糊的、模棱两可的。第二个就是没有太多的禁止项，这个就会导致大模型自入的去进行发散。那么第三个是一个非常非常关键的，大家千万不要觉得，跟随求生里面写的内容越多，那么它的效果就越好。一定不要把它写得过长，建议大家去精简到五百字以内，或者是稍微长一点项目，可以去精简到两千字以内。因为过长反而会去让它产生一些额外的解决以漏项，所以并不一定是长度就能标实你当前对这个项目的把控度越高，这个是它的一个核心的需求。

#### 六原则

[27:40] 当然我们这里面也给大家去制造了写作六原则：

- 写禁止项比写允许项效果更好（"我不允许你干什么" 比 "我允许你干什么" 效果更好）
- 具体一定要大于抽象
- 确定纪律方案可以通过通俗的语言去跟 AI 说为什么要这样做，然后不要去准确的使用一些标准的术语——如果你不太清楚的，你可以和大模型多进行一些沟通，让它把你的大白话去转化成 AI 能够理解的这样一些标准的术语
- 长度核心原则：一定要去写代码的复用策略
- 对当前项目实际的架构要有非常详细的一个描述——如果不知道，就通过大白话的方式跟大模型多进行几轮的沟通，让它把大白话转化成标准的这样一个技术语言
- 专业术语一定要做得足够的精准
