# Harness工程：这才是AI时代工程师正在干的

## 什么是 Harness Engineering？

今天我们来讲一个最近特别火的词——**Harness Engineering**。

首先我们先看一下这个词到底是什么意思。我给大家做一个比方：

> 想象你有一匹马，马很有力量。但是它有力量本身也不太有用。真正让马的力量变得可以使用的是什么？是套在它身上的那套**挽具**——像鞍、项圈、马鞍等等。这个统称就是 **Harness**。

OK，那对于大语言模型来说，现在的 Harness Engineering 为什么这么火？

因为 LLM 也是一样——模型很有能力，它可以说是上知天文、下知地理。但是，模型有能力不代表它能够给出一个好的输出。

所以 Harness Engineering 直观的比方就是：**研究怎么在模型外面套好这套"挽具"，让模型的能力可以被稳定地、可重复地去使用。**

而且 Harness Engineering 不再是单单把 Prompt 提升这样一个概念，它比 Prompt 大一个量级。

---

## LLM 的结构性缺陷

首先要理解 Harness Engineering 这个概念，我们需要知道 LLM 到底有哪些**结构性缺陷**：

| 缺陷 | 说明 |
|------|------|
| **无状态** | 每次对话结束，它什么都不记得 |
| **无法主动访问外部世界** | 只能生成文字，不能主动调用API、执行代码 |
| **上下文限制** | 不能无限制处理信息 |
| **输出概率性** | 同样的输入可能产生不同的输出，无法事先保证哪一次是对的 |

这些都不是 Bug，而是模型本身的基本限制。所以 Harness 要做的，就是**在这些限制的基础上建造一套系统，让模型可以完成原本无法独立完成的任务**。

我用一个更简单的类比：

> 你可以把模型看作是一个**引擎**，Harness 是外面的**车**。
> 
> 如果你的引擎再牛——八缸、十二缸——但是你没有变速箱、没有刹车、没有仪表盘，那你这个车也没办法上路。

---

## Harness 的四层架构

Harness 不是一个具体工具，而是围绕着模型构建的一套基础设施的总称。它可以分成四层：

### 第一层：记忆层

**解决问题**：模型无状态

模型本身不记得之前说过什么，也不知道你的项目有什么规范。

**解决方案**：用文件系统做持久化，把需要模型知道的东西写下来、结构化存放。模型每次工作都能检索到正确的背景信息。

在代码场景里，这通常就是 `CLAUDE.md` 或者 `AGENT.md`。这两个不叫百科全书，而是一个**导航地图**，只告诉 Agent 最关键的约束和规则。

### 第二层：执行层

**解决问题**：模型只能生成文字

**解决方案**：向外部执行——代码运行、浏览网页、调用 API。这些能力让模型真的从"我只是给你讲一些话"变成了"真的我去做这个事情"。

同时 Harness 提供了**沙箱环境**，确保它的试错成本低。Agent 在隔离的工作区里可以大胆改动，改坏了直接丢掉，不影响主分支。

### 第三层：反馈层

**解决问题**：模型输出不可靠

这是整个 Harness 框架里最核心的部分。

**工具构成**：测试、Linter、CI 流水线——这些工具构成了对模型产出的**确定性验证机制**。

模型生成代码后，测试自动跑一遍：
- 不通过 → 自动打回重试
- 通过了 → 才能进入下一步

反馈的速度从人工 review 的小时级缩短到秒级。这个回路能够闭环的根本原因在于：**代码有一种特殊性质——生成虽然是有概率性的，但是验证是确定性的。**

> 你不需要模型每次都对，你只需要有足够好的验证手段就够了。

### 第四层：编排层

**解决问题**：复杂任务的拆解

一个大的任务不可能都交给一个模型去做，可能会拆成几个并行的子任务，多个 Agent 分工协作。中间可能会有 **Hook** 和中间件的协调状态，让系统可以处理远超单次对话能力上限的工程任务。

## 为什么代码领域是突破口？

AI 在很多领域都有应用，但 Harness Engineering 完全投入在代码场景发展是最快、最系统的。

**原因在于一个不对称性**：

| 特性 | 代码领域 | 其他领域 |
|------|----------|----------|
| 生成 | 概率性 | 概率性 |
| 验证 | **确定性** | 很难自动判断 |
| 反馈速度 | 秒级 | 需要人工 |

代码的生成是概率性的，但验证是确定性的：
- 编译器不会因为你今天心情好就放过一个语法错误
- 测试不会因为你的态度端正就假装通过

这种确定性让反馈回路在代码领域可以做到**完全自动化**。

相比之下：
- 写一篇文章到底对不对？
- 做一个视频内容看它到底好不好？
- 设计好不好看？

这些问题很难用机器自动判断。

**这意味着什么？**

Agent 在代码领域犯错 → 系统立刻打回 → Agent 修正后 → 系统再次验证 → 这种循环可以高速运转，不需要人盯着。

但注意，有一个容易忽略的前提：**验证基础设施本身要足够好**。

没有测试，拿什么验证？没有 Lint 规则，怎么去自动执行约束？

过去这些工程实践被称为"最佳实践"，大家都觉得重要但可以拖。但在 AI 时代，付出的代价完全不同——一个没有约束的 Agent 会以机器速度全天候地给你制造屎山。

---

## 核心要点总结

1. **Harness Engineering** = 为模型构建外部约束系统，让能力可稳定、可重复地转化为价值
2. **四层架构**：记忆层 → 执行层 → 反馈层 → 编排层
3. **代码领域的优势**：生成概率性 + 验证确定性 = 可自动化闭环
4. **前提条件**：验证基础设施（测试、Lint、CI）要足够好
5. **时代变化**：没有约束的 Agent 会以机器速度制造问题，"最佳实践"的代价被放大

> 关键理念：你不需要模型每次都对，你只需要有足够好的验证手段。
