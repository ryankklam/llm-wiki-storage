# 生成-评估-修复循环

## 定义

**生成-评估-修复循环（Generate-Evaluate-Repair Loop）是一种 Agent 架构模式**，将复杂任务拆分为三个独立的 Prompt 系统，通过迭代方式提高输出质量。这是构建高可靠性 Agent 的推荐方案。

## 核心架构

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   生成器     │ ──▶ │   评估器     │ ──▶ │   修复器     │
│ (Generator) │     │ (Evaluator) │     │  (Repairer) │
└─────────────┘     └─────────────┘     └─────────────┘
      │                   │                   │
      ▼                   ▼                   ▼
   生成初稿           检查违规           针对性修复
```

### 三个组件

1. **生成器（Generator）**
   - 创建输出的初稿
   - 使用简单的 Prompt
   - 不需要一次做对所有事情

2. **评估器（Evaluator）**
   - 检查输出是否满足要求
   - 报告具体的违规
   - 提供违规的证据

3. **修复器（Repairer）**
   - 接收违规报告
   - 进行针对性修复
   - 输出改进后的结果

## 与单 Prompt 方案对比

| 方案 | 优点 | 缺点 |
|------|------|------|
| 单个大 Prompt | 简单 | 难以调试、tokens 消耗大 |
| 生成-评估-修复循环 | 可靠、tokens 少、延迟低 | 需要维护多个 Prompt |

## 实际案例：员工排班表

### 问题
- 8 名员工
- 需要满足的约束条件
- 硬性规则检查

### 方案对比

| 方案 | 结果 | Tokens | 延迟 |
|------|------|--------|------|
| Sonnet 4.6 + 简单 Prompt | 全部失败 | 高 | 低 |
| Opus 4.7 + Extended Thinking | 全部通过 | 很高 | 很高 |
| 生成-评估-修复循环 | 全部通过 | 低 | 低 |

## 关键优势

### 1. 运行时灵活性

可以在评估 Prompt 中输入软约束，无需修改后端代码：
- "Harry 不喜欢和 Sally 一起工作，尽量把他们分开"
- "周三需要一个额外班次"

### 2. 更好的可维护性

- 每个 Prompt 职责单一
- 易于调试和优化
- 可以独立迭代每个组件

### 3. 更高的效率

- 避免在一个大 Prompt 中完成所有事情
- 减少不必要的 tokens 消耗
- 降低延迟

## 适用场景

- 需要高可靠性的任务
- 有明确的规则需要满足
- 需要支持运行时软约束
- 单个 Prompt 难以完成复杂任务

## 最佳实践

1. **保持每个 Prompt 简单**：每个组件只做一件事
2. **清晰的接口**：定义好组件之间的数据传递格式
3. **迭代优化**：可以多次运行评估-修复循环
4. **结合程序化检查**：对于硬性规则，使用 Python 函数检查
