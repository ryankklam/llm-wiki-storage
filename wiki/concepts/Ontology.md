# Ontology

> Ontology 不是为了表示数据，而是为了表示决策。

## 定义

Ontology（本体）是 Palantir 的核心语义建模层，用于在企业数据之上构建统一的语义系统。它把企业里所有的概念（人、设备、订单、产线、物料、排产计划）全部定义成可以被调用的对象，每个对象都知道自己是谁、有什么属性、跟谁有关系、能被怎么操作。

## 核心组件

Palantir 把 Ontology 拆成四个核心组件：

### Object Type
定义企业里有什么类型的对象：
- 设备是一个类型
- 产线是一个类型
- 订单是一个类型

### Property
定义每个类型的特征：
- 设备有型号、状态、上次维护时间

### Link Type
定义类型之间的关系：
- 一台设备属于哪条产线
- 一个订单关联了哪台设备

### Action Type
定义能对对象做什么操作：
- 关闭一台设备
- 修改一个订单的状态
- 把一条产线从白班切换到夜班

## 核心洞察

Palantir 文档的核心观点：**Ontology 不是为了表示数据，而是为了表示决策**。数据只是支撑决策的原料。

这个区别是理解 Ontology 价值的关键：
- 传统系统：查三号工厂设备利用率 → 得到一张表 → 自己判断
- Ontology：设备利用率是否低于阈值？如果是，触发什么动作？→ 决策链路

## 与数据中台的区别

| 数据中台 | Ontology |
|---------|----------|
| 解决可视化问题 | 解决决策问题 |
| 你告诉我你要什么数据 | 你告诉我你要解决什么问题 |
| 先铺管道再想怎么用 | 先想清楚问题，再决定对象 |
| 搬家：把东西搬进来 | 装修：按生活方式重新设计 |

## Embedded Ontology

Palantir 把 Ontology 搬到了设备端，实现了分布式数据架构：
- 定义一个投影，把跟用户相关的 Ontology 子集搬到设备上
- 离线状态下所有查询和操作跑在本地 Ontology 上
- 联网后自动同步回云端

这不是缓存优化，而是让设备成为整个数据系统的一个自治节点。

## 为什么重要

Ontology 是 FDE 模式能跑通的唯一前提：
- 没有 Ontology，FDE 是穿着工程师外套的昂贵顾问
- 有了 Ontology，FDE 才是反向传播的人类等价物

FDE 不需要从零学习企业的数据结构和命名规则，打开编辑器，所有对象都在代码提示里。
