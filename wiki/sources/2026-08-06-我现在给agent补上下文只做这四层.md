# 我现在给 agent 补上下文，只做这四层

> 上下文不是给模型补充更多知识，而是给它当前决策所需要的真实事实。给 Agent 补上下文，不再追求"给的更多"，而是追求在当前任务里能不能让它找到真正有效的信息。作者将Agent上下文分为四层：项目地图（AGENTS.md）、按需知识（知识树）、任务现场（动态组装）、长期记忆（稳定结论筛选）。

## 核心观点

1. **上下文 ≠ 更多知识**：Agent能看到的资料越来越多，并不意味着理解越来越准确。上下文越多，规则越多，互相冲突的内容越多，Agent最终可能拿着一堆资料却没有拿到当前任务真正需要的那个事实
2. **上下文 = 当前决策所需的真实事实**：即使这个事实很小（如准确时间、营业日定义、节假日规则）
3. **四层上下文架构**：项目地图 → 按需知识 → 任务现场 → 长期记忆
4. **AGENTS.md精简化**：从操作手册变为项目地图，只回答三个问题——项目是什么、重要信息在哪里、有哪些不能违反的业务边界
5. **按需加载不是按量加载**：知识树分层组织，Agent按任务需要查询对应分支
6. **任务现场是关键层**：前面的两层都是相对静态的，而任务现场每次任务都不一样
7. **长期记忆只留稳定结论**：不是什么都记住，而是知道什么值得留下，以及什么时候重新拿出来

## 视频章节

### 一、重新定义上下文
- [00:00] 给Agent补充上下文，不是把Prompt写更长、文档全部塞进知识库、接一个RAG
- [00:30] Agent能看到的资料越来越多，并不意味着理解越来越准确——上下文越多，冲突越多
- [01:00] 典型问题：Agent代码写得对、测试通过了，但选错了应用日期——运行结果是错的
- [01:35] 模型缺的不是日期处理逻辑，而是准确时间、时区、营业日定义、节假日规则、历史代码口径

### 二、四层上下文架构

#### 第一层：项目地图（AGENTS.md）
- [02:40] 以前AGENTS.md像操作手册：先分析、先搜索、要测试、不要改无关代码、要总结
- [03:10] 随着模型变强，很多内容没必要写这么详细——模型本身已经知道要测试、要搜索
- [03:25] 现在AGENTS.md精简为地图，只回答三个问题：项目是什么、重要信息在哪里、有哪些不能违反的业务边界

#### 第二层：按需知识
- [03:50] 把会议纪要、历史决策、业务规则和排查经验，整理成可以逐层查询的知识树
- [04:05] 不是一次性全部塞给Agent，而是让Agent知道有这棵知识树存在，需要时主动查询
- [04:20] 按需加载，不是按量加载

#### 第三层：任务现场
- [04:40] 每次任务开始时，动态组装当前Issue、相关代码、业务口径、准确时间、环境和日志状态
- [04:55] 最关键的一层——前两层是相对静态的，任务现场每次都不一样

#### 第四层：长期记忆
- [05:30] 只留下稳定的结论、决策、风险和验证结果，而不是把所有历史过程都永久保留
- [05:45] 先沉淀进知识库，等未来遇到相关问题时再按需加载
- [05:55] 好的记忆不是什么都记住，而是知道什么值得留下，以及什么时候重新拿出来

### 三、总结
- [06:50] 补上下文不是写一份越来越长的说明书，而是让Agent知道：现在在哪里、正在处理什么问题、应该去哪里寻找事实、哪些经验值得在下一次继续使用
- [07:10] 真正好的上下文系统，不是让Agent每次都读得更多，而是让它每次只读对的东西
- [07:20] 上下文解决了Agent知道什么，下一期聊怎么把人工操作转化为Agent可以持续执行的任务工具
