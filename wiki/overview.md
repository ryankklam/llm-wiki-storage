### Ontology与数字孪生
> Ontology（本体）是 FDE 的地基，决定了数字孪生的表达能力。

Palantir 的护城河不是算法，而是 Ontology——把任何行业的数据都能映射成对象模型的能力：
- **实体（Object）**：现实世界的对象

- **关系（Link）**：实体间的关联
- **动作（Action）**：对实体的操作

### Agent分类体系
Agent按产出类型可分为两大类：
1. **Coding Agent**（Claude Code、Codex、OpenCode）：产出代码，预装完整工具链
2. **日常任务Agent**（Pi Agent）：产出结果，极简底座 + Skill按需扩展

### Pi Agent的核心优势
- System Prompt不到1500 tokens（Claude Code约20000 tokens）
- 三大优势：快、省（token消耗约1%）、聪明（注意力集中）
- 核心公式：Agent + Skill = 最基本的框架

### Skill生态
- Skill是给Agent的说明书/操作手册
- 按需安装，支持global和project两种模式
- 覆盖搜索、文件读取、语音合成、图片生成、视频制作等场景

### Context Window优化策略
上下文窗口是LLM的"桌面"，会抢位置的东西包括：系统规则、当前任务、历史对话、RAG证据、工具结果、记忆。

**优先级排序**：
1. 系统规则（最高）
2. 当前用户请求和关键约束
3. 高相关证据（RAG结果）
4. 最近几轮对话
5. 长期偏好摘要

**核心原则**：上下文不是越多越好，关键是把当前任务需要的东西留下，把过期和敏感内容挡住。

### 记忆管理体系
- **短期记忆**：服务当前会话，策略包括滑动窗口、摘要压缩、重要事实抽取
- **长期记忆**：服务跨会话，写入前要问三件事（稳定吗？有用吗？敏感吗？）
- **脏记忆防护**：写入有门槛、读取按相关性、过期敏感内容可删除

### Agent范式体系
AI Agent 的四种范式并非同层级对比对象，而是分属不同维度：

| 范式 | 层级 | 核心问题 |
|------|------|----------|
| Tool Use | 基础能力层 | 模型能否调用外部工具？ |
| ReAct | 推理框架层 | 推理和行动如何交替？ |
| Plan-and-Execute | 控制流程层 | 先规划还是边想边做？ |
| Multi-Agent | 组织架构层 | 多个 Agent 怎么协作？ |

**关键认知**：四种范式可以叠加而非互斥。选型不是四选一，而是根据场景在每一层做组合决策。

**核心原则**：用最少的复杂度解决当前问题。范式越高级，系统复杂度越高，复杂度本身就是成本。

### Anthropic 数据 Agent 四层架构
> Anthropic 把数据分析当成上下文和验证问题来处理，通过四层系统实现 95% 场景自助分析和 90% 准确率。

| 层级 | 名称 | 核心职责 | 类比 |
|------|------|----------|------|
| 第一层 | 数据基础 | 整理数据世界，收窄答案空间 | 画地图 |
| 第二层 | 可信来源 | 确定信息优先级和来源可信度 | 规定路线 |
| 第三层 | Skills | 编码资深分析师的工作流程 | 驾驶规则 |
| 第四层 | 验证 | 持续检查和纠错 | 复盘检查 |

**关键数据**：
- 无 Skills 时准确率：最高不超过 21%
- 有 Skills 后准确率：稳定超过 95%，部分领域接近 99%
- 对抗审查：准确率 +6%，代价 Token +32%、延迟 +72%

**最有价值的消融实验发现**：直接喂全量 SQL 语料准确率提升不到 1%。关键在于信息的结构化编排，而非信息量。

**核心结论**：企业要做数据 Agent，不要一开始就对资料和权限。先画出答案路径，再让 Agent 沿这条路径工作。这比指望模型自己变聪明要可靠得多。

**最小可行版本**：少量官方数据集 + 基础语义层 + 离线评测 + 薄的 Knowledge Skill。

### Agent Loop 与 Loop Engineering
> 2026 年下半年硅谷最火的概念，代表从 Prompt 工程到系统工程的范式转移。

Anthropic 创始人 Lior Shternberg 和 Claude Code 创始人 Boris 都公开表示应该停止写 Prompt，转向为 Agent 设计 Loops。

**Agent Loop 的五大构件 + Memory 层**：

| 构件 | 核心职责 |
|------|----------|
| Agent 自动化 | Agent 自身的执行能力 |
| Tools（工具层） | Agent 调用外部工具的能力 |
| Skills（技能层） | 指令 + 元数据 + 脚本/资源，沉淀经验供复用 |
| Supervisor（监督代理层） | Planner 和 Checker 分离，独立评审输出质量 |
| Memory（记忆层） | Markdown 文件，每轮对话加载 |

**设计五步法**：
1. 定义停止条件（最重要，必须可代码化）
2. 构建 Context 上下文（根据 State 自动组装）
3. 执行并捕获
4. 反馈
5. 设置 Guardrails 护栏（最大迭代次数 15-50 次、无进展检测、Token 上限）

**Token 优化关键策略**：协调者只路由不推理——协调者输出只是路由方向（如 12345），可以非常短。所有 LLM 模型输出成本大于输入成本，省输出是四两拨千斤。

**Loop Engineering 的核心认知**：不是让工作变容易，而是难点上移。原来 Prompt 工程师协调指令，现在 Loop Engineering 要求设计一个能够持续、可验证地运行来完成复杂任务的系统。

### 直播卖券的经济学逻辑
> 直播卖券不是简单的降价，而是一套集价格歧视、预付款融资、用户锁定、品牌保护于一体的精细化经营动作。

瑞幸等品牌的直播卖券策略包含四层逻辑：
1. **价格歧视**：通过麻烦程度自动筛选价格敏感型用户，让不同支付意愿的人支付不同价格
2. **预付款融资**：把未来不确定的消费变成今天确定的现金流
3. **沉没成本锁定复购**：已购券在用户心理制造沉没成本，提前锁定后续消费
4. **保护价格锚点**：把低价放进特殊场景（限时专属福利），避免消费者对"正常价格"的认知被永久改写

表面多了一层成本（主播、平台抽成），实际省下来的是利润、用户心智和未来提价空间。
