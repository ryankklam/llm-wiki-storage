### rules.md / CLAUDE.md 工业级应用范式
> 企业 AI 项目 rules 红线怎么立，5 条硬规矩 + 6 个写法门道，500 字以内写出工业级应用范式。

真正拉开企业级工程师和普通人差距的，是能不能让 AI 按规则入手：
- **五条硬规矩**：先写清项目不是什么、量化可验证、做和不做都列清楚、技术栈写版本号、压在 500 字以内
- **六个写法门道**：禁止项优先、给理由、具体大于抽象、写复用策略、术语精准、控制长度
- **核心心法**：管 AI 跟管项目，本来就是同一件事。把 rules.md 立在 Markdown 文档里，立在工程最前面，比后面任何补救都管用

### Spec-Kit：企业级 Spec 驱动开发框架
> Anthropic 官方开源的 Spec-Kit，通过五条核心命令 + 两道可选关卡构建 AI 编程的最小闭环。

Spec-Kit 是 Anthropic 官方开源的 Spec 驱动开发框架，专门配 Claude Code、Cursor、Copilot 使用。相较于轻量框架 OpenSpec，Spec-Kit 解决了三大核心问题：

| 问题 | OpenSpec | Spec-Kit |
|------|----------|----------|
| 从零起步 | 无引导式提问 | Constitution 立宪法 |
| 需求澄清 | 不主动追问 | Clarify 主动追问 |
| 校验 | 依赖人工经验 | Verify 内置一致性校验 |

**五条核心命令（最小闭环）**：立宪法 → 说需求 → 出方案 → 拆任务 → 生成

**两道可选关卡**：主动追问（Clarify）、一致性检查（Verify）

**核心理念**：让 AI 停下来等你点头，比让 AI 跑得快更重要。方法是通用的，工具换成 Cursor、Claude Code、Codex 都成立，模型换下一代也成立。

**五大组件系统**：CLI 主体、AI Agent 注册中心、扩展系统（Extension，做加法）、预设系统（Preset，做替换）、工作流引擎（Workflow）

### Agent分类体系
Agent按产出类型可分为两大类：
1. **Coding Agent**（Claude Code、Codex、OpenCode）：产出代码，预装完整工具链
2. **日常任务Agent**（Pi Agent）：产出结果，极简底座 + Skill按需扩展

### Pi Agent的核心优势
- System Prompt不到1500 tokens（Claude Code约20000 tokens）
- 三大优势：快、省（token消耗约1%）、聪明（注意力集中）
- 核心公式：Agent + Skill = 最基本的框架

### Skill生态
- Skill是给Agent的说明书/操作手册
- 按需安装，支持global和project两种模式
- 覆盖搜索、文件读取、语音合成、图片生成、视频制作等场景

### Context Window优化策略
上下文窗口是LLM的"桌面"，会抢位置的东西包括：系统规则、当前任务、历史对话、RAG证据、工具结果、记忆。

**优先级排序**：
1. 系统规则（最高）
2. 当前用户请求和关键约束
3. 高相关证据（RAG结果）
4. 最近几轮对话
5. 长期偏好摘要

**核心原则**：上下文不是越多越好，关键是把当前任务需要的东西留下，把过期和敏感内容挡住。

### 记忆管理体系
- **短期记忆**：服务当前会话，策略包括滑动窗口、摘要压缩、重要事实抽取
- **长期记忆**：服务跨会话，写入前要问三件事（稳定吗？有用吗？敏感吗？）
- **脏记忆防护**：写入有门槛、读取按相关性、过期敏感内容可删除
- **生产级Agent记忆架构**：四层分层（会话元数据→结构化档案→对话摘要→滑动窗口）+ 状态管理三件套 + 双时间机制 + 程序性经验沉淀

### Agent范式体系
AI Agent 的四种范式并非同层级对比对象，而是分属不同维度：

| 范式 | 层级 | 核心问题 |
|------|------|----------|
| Tool Use | 基础能力层 | 模型能否调用外部工具？ |
| ReAct | 推理框架层 | 推理和行动如何交替？ |
| Plan-and-Execute | 控制流程层 | 先规划还是边想边做？ |
| Multi-Agent | 组织架构层 | 多个 Agent 怎么协作？ |

**关键认知**：四种范式可以叠加而非互斥。选型不是四选一，而是根据场景在每一层做组合决策。

**核心原则**：用最少的复杂度解决当前问题。范式越高级，系统复杂度越高，复杂度本身就是成本。

### Anthropic 数据 Agent 四层架构
> Anthropic 把数据分析当成上下文和验证问题来处理，通过四层系统实现 95% 场景自助分析和 90% 准确率。

| 层级 | 名称 | 核心职责 | 类比 |
|------|------|----------|------|
| 第一层 | 数据基础 | 整理数据世界，收窄答案空间 | 画地图 |
| 第二层 | 可信来源 | 确定信息优先级和来源可信度 | 规定路线 |
| 第三层 | Skills | 编码资深分析师的工作流程 | 驾驶规则 |
| 第四层 | 验证 | 持续检查和纠错 | 复盘检查 |

**关键数据**：
- 无 Skills 时准确率：最高不超过 21%
- 有 Skills 后准确率：稳定超过 95%，部分领域接近 99%
- 对抗审查：准确率 +6%，代价 Token +32%、延迟 +72%

**最有价值的消融实验发现**：直接喂全量 SQL 语料准确率提升不到 1%。关键在于信息的结构化编排，而非信息量。

**核心结论**：企业要做数据 Agent，不要一开始就对资料和权限。先画出答案路径，再让 Agent 沿这条路径工作。这比指望模型自己变聪明要可靠得多。

**最小可行版本**：少量官方数据集 + 基础语义层 + 离线评测 + 薄的 Knowledge Skill。

### Loop Engineering 面试精讲：五大组件与三大风险
> 一线大厂AI工程师面试精讲Loop Engineering，从面试视角拆解Loop的核心概念。

Loop Engineering 是第四代 Agent 工程范式，建立在 Prompt、Context、Harness 三代工程之上。四者不是替代关系，而是层叠关系——Loop 在最上层调度一切。

**面试视角的五大组件**：

| 组件 | 核心职责 | 面试关键点 |
|------|----------|------------|
| 明确的目标 | Agent 自己能判断是否达成 | 可验证的定义，如单元测试通过 |
| 上下文管理 | 压缩、摘要、检知策略 | 防止撑爆 Token 上限 |
| 可调用的工具 | 终端、文件系统、测试运行器 | 循环质量取决于反馈真实性 |
| 产出评估 | 跑测试、LLM 打分、对比 Diff | 没有评估循环就失去方向 |
| 停止条件 | 目标达成停、最大次数停、无进展停 | 直接影响 Token 成本和产出质量 |

**Loop 与 Harness 的关系**：Harness 是舞台，Loop 是剧本。Harness 搞定能不能跑，Loop 保证跑得对不对。

**三大核心风险与对抗手段**：
1. 无限循环 → 硬性迭代上限 + 无进展检测
2. 目标飘移 → 每轮目标对照 + 持久化存储
3. Context 溢出 → 压缩与裁剪

**核心结论**：Loop Engineering 的竞争力不在单次回答，而在于循环的收敛速度和验证的完备程度。它标志着人在 AI 工作流中从逐句指挥进化为系统设计。

### Agent Loop 与 Loop Engineering
> 2026 年下半年硅谷最火的概念，代表从 Prompt 工程到系统工程的范式转移。

Anthropic 创始人 Lior Shternberg 和 Claude Code 创始人 Boris 都公开表示应该停止写 Prompt，转向为 Agent 设计 Loops。

**Agent Loop 的五大构件 + Memory 层**：

| 构件 | 核心职责 |
|------|----------|
| Agent 自动化 | Agent 自身的执行能力 |
| Tools（工具层） | Agent 调用外部工具的能力 |
| Skills（技能层） | 指令 + 元数据 + 脚本/资源，沉淀经验供复用 |
| Supervisor（监督代理层） | Planner 和 Checker 分离，独立评审输出质量 |
| Memory（记忆层） | Markdown 文件，每轮对话加载 |

**设计五步法**：
1. 定义停止条件（最重要，必须可代码化）
2. 构建 Context 上下文（根据 State 自动组装）
3. 执行并捕获
4. 反馈
5. 设置 Guardrails 护栏（最大迭代次数 15-50 次、无进展检测、Token 上限）

**Token 优化关键策略**：协调者只路由不推理——协调者输出只是路由方向（如 12345），可以非常短。所有 LLM 模型输出成本大于输入成本，省输出是四两拨千斤。

**Loop Engineering 的核心认知**：不是让工作变容易，而是难点上移。原来 Prompt 工程师协调指令，现在 Loop Engineering 要求设计一个能够持续、可验证地运行来完成复杂任务的系统。

### Loop Engineering 实践：五个核心组件
> 从实践角度，一个 Loop 需要五个组件和一个 State 记忆系统。

| 组件 | 核心职责 |
|------|----------|
| Automations | Loop 的心跳，按节奏醒来，去看 Issue、CI、Commit |
| Worktrees | 给每个 Agent 独立的 Checkout，避免文件冲突 |
| Skills | 把项目约定写成文件，避免每次冷启动 |
| Plugins 和 Connectors | 通过 MCP 让 Agent 接触真实工具 |
| Sub-Agents | Maker 和 Checker 分开，写代码的不给自己盖章 |
| State | 记住做过什么、通过什么、还剩什么 |

**Claude Code vs Cursor 实现**：Claude Code 有 Automations Tab、内建 Worktrees、Agent Skills、MCP Plugins、Sub-Agents；Cursor 有 Agents、Queues 和 Hooks、Git Worktree、Skills、MCP Service、Agent Teams。名字不同，能力本质相同。重点不是按下某个按钮，重点是设计一个换了工具也还能跑的工作回路。

**Loop 的三大风险**：
1. **验证责任**：Agent 说"done"只是主张不是证明，测试/Review/上线后信号才是证据
2. **认知距离**：Loop 越快交付你没写的代码，你和系统之间的距离越大
3. **渐进式放弃**：当系统看起来能自己跑，人容易停止判断，慢慢改变工作习惯

**核心结论**：构建 Loop，但继续做工程师。

### Agent Skill 路由：从匹配到检索的范式转移
> 当 Agent 的 Skill 从十几个涨到上百个后，路由本身从简单匹配演变成了检索问题。

Skill 过多导致模型"抽风"——明明有对应 Skill 却不用，或者用了错误的 Skill。这不是模型变笨了，而是需要系统化的路由优化策略：

1. **优化 Skill 描述**：Name 和 Description 是向量检索的标题和摘要，要写触发场景而非功能介绍
2. **建立 Skill Tree 分层路由**：大类 → 子类 → 具体 Skill，搜索空间大幅缩小
3. **增加负样本描述**：When Not to Use 能显著减少误触发
4. **引入召回加重排**：Embedding 召回 Top 10 + LLM 精排，与 RAG 同构

**核心思想（Anthropic Progressive Disclosure）**：Claude 不会把所有 Skill 全部塞进上下文，而是先读取 Name 和 Description，再决定要不要加载完整内容。Skill 路由本质上就是一个检索系统。

### 直播卖券的经济学逻辑
> 直播卖券不是简单的降价，而是一套集价格歧视、预付款融资、用户锁定、品牌保护于一体的精细化经营动作。

瑞幸等品牌的直播卖券策略包含四层逻辑：
1. **价格歧视**：通过麻烦程度自动筛选价格敏感型用户，让不同支付意愿的人支付不同价格
2. **预付款融资**：把未来不确定的消费变成今天确定的现金流
3. **沉没成本锁定复购**：已购券在用户心理制造沉没成本，提前锁定后续消费
4. **保护价格锚点**：把低价放进特殊场景（限时专属福利），避免消费者对"正常价格"的认知被永久改写

表面多了一层成本（主播、平台抽成），实际省下来的是利润、用户心智和未来提价空间。

### 密码安全：后端面试的安全底线
> 面试官问"用户密码怎么存"，答MD5直接被淘汰。这道题考的是安全底线和工程素养，从为什么不行到现在怎么做，一路讲清楚才能过关。

密码存储设计必须吃透三层核心逻辑：
- **第一层：为什么MD5不行**：MD5是哈希不是加密，算得太快，彩虹表和暴力破解面前几乎等于明文
- **第二层：加盐（Salt）**：每个用户不同随机盐，废掉彩虹表，相同密码也存出不同哈希
- **第三层：慢哈希算法**：BCrypt、SCrypt、Argon2故意设计得慢，通过计算成本因子（Work Factor）让暴力破解成本不可承受。正常登录无感，破解贵到上天

**核心分水岭**：普通后端答"MD5加密"直接暴露安全认知停在10年前；有安全底线的后端能从明文→快哈希→加盐→慢哈希一路讲明白。

### 缓存一致性：后端面试经典题
> 商品库存存在Redis里，怎么保证缓存和数据库的数据一致性？面试官考察的不是你会不会背策略，而是你在任何异常场景下都能保证数据最终一致。

缓存一致性设计必须吃透三层核心逻辑：

**第一层：基础方案拆解**
- 先更新数据库再删缓存是最优基础方案，但要解决删缓存失败问题
- 先删缓存再更新数据库会引发并发读写脏数据
- 延迟双删只能缓解不能根治
- 双写数据库和缓存是最差方案

**第二层：生产级一致性方案**
- 基于Canal监听数据库变更，异步删除缓存（互联网公司通用方案）
- 版本号校验：查询缓存时带上版本号，不一致则刷新
- 读写分离特殊处理：主从延迟场景下强制读主库

**第三层：异常兜底与极限防护**
- 重试机制：删缓存失败时加入消息队列，最多重试三次
- 缓存过期兜底：所有缓存必须设置合理TTL
- 监控告警：监控缓存命中率、脏数据次数、删缓存失败率
- 最终对账：每天凌晨比对缓存和数据库数据，修复不一致记录

**核心分水岭**：普通后端背个先更新库再删缓存，出问题只会加过期时间；大厂后端能随手设计一套基于异步兜底加最终对账的一致性体系。
